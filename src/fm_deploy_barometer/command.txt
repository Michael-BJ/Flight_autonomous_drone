============================================================
PARAMETER REFERENCE
============================================================
The "default" column = the default in fm_all_barometer.launch.py.


1. MISSION & GEOMETRY
------------------------------------------------------------
goal_dist:=6.0            default 5.0
    Goal distance AHEAD of home, along the nose direction at arming
    (home frame). Paired with goal_lat (0 = straight, + = shift left).
    The forward geofence is 10 m, so 6 m is still inside the fence.

target_alt:=2.0           default 2.0
    Cruise height ABOVE THE TAKEOFF POINT (ground_z), not AMSL.
    Do not go below 2.0 m: the octomap band lives in the drifting EKF
    frame; below that, ground returns enter the band and the planner
    stops moving.

v_max:=0.3                default 0.5
    Maximum speed used by the optimizer. If the trajectory peak exceeds
    it, the whole trajectory duration is stretched by a factor k -> see
    the log line "[TRAJ] ... scale k=". A healthy k is 1.0-1.2.


2. PLANNER
------------------------------------------------------------
replan_period:=2.0        default 1.0
    Time between replans. A guard that cancels the trajectory triggers
    an earlier replan (minimum gap 0.3 s).
    NOTE: the 9/15 test showed w_feasibility=1000 + replan 2.0 s is the
    worst combination (45% of the time stopped, 0.18 m/s) because the
    trajectory runs out and the drone waits for the next replan. With
    replan 1.0 s -> 0.49 m/s. The 9/16 flights used 2.0 and logged
    spd 0.17-0.25 with v_max 0.30. Prefer replan_period:=1.0.

planning_time_ahead:=0.3  default 0.3
    The setpoint is taken from the trajectory point 0.3 s AHEAD of now,
    to cover the computation delay. Too large -> the drone flies faster
    than v_max (9/15 test: ahead 0.6 -> 0.64 m/s with v_max 0.5).

w_feasibility:=1000.0     default 1000.0
    Weight of the speed violation in the MINCO cost. With the old weight
    (1.0) the optimizer planned 2-3x v_max, the trajectory was slowed by
    k, and the start velocity was divided by k again at the next replan
    -> the drone almost stood still (9/15). Old behaviour:
    w_feasibility:=1.0.

max_plan_cost:=1000       default 50
    Quality gate: trajectories with a total cost above this are rejected.
    1000 = EFFECTIVELY OFF; numerically exploding solutions (wildly
    swinging paths) are accepted too.


3. GUARDS THAT ARE TURNED OFF
------------------------------------------------------------
use_lookahead_guard:=false   default true (in this launch)
    Turns off the guard that checks ahead along the trajectory and
    cancels it when it enters unmapped space or gets too close.

use_speed_limit:=false       default true
    Turns off the clearance-proportional speed limit
    (speed = margin / k, floor 0.15 m/s). Without it the drone can reach
    an obstacle too fast to brake.

blind_abort_s:=0             default 10 s
    Turns off the OFF-MAP abort (the drone's octomap cell unknown for
    N seconds). This abort is what ended the 9/13 15:05 flight.

stuck_abort_s:=0             default 60 s
    Turns off the "no progress toward the goal for N seconds" abort.

gate_enabled:=false          default true
    Turns off the height gate in depth_to_pointcloud (normally depth
    frames are processed only while the drone is in a height band).
    RIGHT to turn off: on 9/14 the gate computed ground_z wrongly
    (3.58 -> 0.00) and stayed closed the whole flight; the map was empty.

STILL ACTIVE even with all of the above off:
    the hard post-check in _validate_planned_traj (0.55 m from the
    centre) and collision_cost_tol still reject trajectories that hit
    obstacles THAT ARE IN THE MAP. So it is not zero protection. What is
    lost is protection against obstacles NOT YET MAPPED and all emergency
    reactions. In an open field the Gemini 2 depth often has only 0-4%
    valid pixels, so the map is empty -> effectively flying without
    avoidance. OPEN FIELDS ONLY.

Always active without writing anything: geofence (fwd 10 / back 3 /
lat +-4 m, abort radius 12 m), height limits, battery, unexpected-disarm
detection, RC override, and the kill switch (SwF / CH11).


4. HEIGHT
------------------------------------------------------------
max_alt_error:=0.7        default 0.5
    Deviation from target_alt that triggers an ABORT -> land in place.
    The 9/15 09:42 flight hit this abort.

baro_gain:=0.0            default 0.0
    0 = NO barometer correction loop. Setpoint z = ground_z +
    target_alt, and every height check uses the EKF z.
    Reason: PX4 itself provides the height (barometer since 9/14,
    H-Flow range finder with barometer fallback since 10/19), so a gain
    of 0.7 used the same sensor twice and the drone bobbed up and down.
    Old behaviour: baro_gain:=0.7.
    The pre-takeoff barometer gate and the "barometer stream lost" abort
    (5 s) STAY active even with gain 0.


5. MISSION LIMITS
------------------------------------------------------------
min_battery_pct:=20       default 0 (off)
    Below this -> ABORT. Battery counts as a "vehicle problem", so the
    drone LANDS IN PLACE, it does NOT return. This is why the 9/16 12:14
    flight landed at the goal even with rth_after_goal:=true.
    TAKE OFF WITH A FULL BATTERY; do not lower this to 5.

mission_timeout_s:=120    default 180
    Time limit of the FLYING phase. Unlike the battery, a timeout is a
    RECOVERABLE stop, so with RTH on the drone flies home instead of
    landing in place.


6. RETURN TO HOME
------------------------------------------------------------
rth_after_goal:=true      default false
    After the goal is REACHED the drone also flies home and lands there.
    Without it the drone lands at the goal. Adds roughly goal_dist / 0.3
    seconds of flight time.

rth_mode:=replan          default trail
    trail  = fly backwards along the breadcrumb trail recorded every 0.3 m.
    replan = the way home is REPLANNED by the FM planner (the same loop
             as the outbound leg), and the nose turns toward home
             (RTHYAW fix, 9/16).
    A stop by RC / link loss / kill still stops the setpoints at once;
    no RTH.


7. DISPLAY & SAFETY
------------------------------------------------------------
flying_yaw_mode:=smooth   default home
    home     = nose LOCKED toward the goal during FLYING. This is why the
               yaw never changed in all 20 flights on 9/15-9/16
               (62-71 deg measured on 9/16 14:14).
               On RETURN (rth_mode:=replan): turns ONCE to face home,
               then stays locked in that direction until arrival.
    smooth   = nose follows the path direction: smoothed (tau 1.5 s),
               limited to +-60 deg from the goal direction, rate
               <= 30 deg/s, deadband 15 deg, holds when the speed is
               < 0.05 m/s.
               On RETURN (rth_mode:=replan) the nose turns to face home
               at 30 deg/s right away, even when slow or hovering.
               (YAWFIX 9/30: before, tau 1.0 and min 0.15 m/s -> the nose
               almost never moved, and on 9/23 17:19 RETURN flew 80 s
               with the nose 60 deg off home.)
               Calmer: yaw_smooth_tau_s:=2.0 | faster: 1.0
    velocity = old behaviour; makes the drone spin in place (9/15
               00:53). Do not use.
    Tuning: yaw_rate_max_dps, yaw_deadband_deg, yaw_smooth_tau_s,
    yaw_max_offset_deg, yaw_min_speed.
    smooth flew once (9/23 17:19, before YAWFIX); the YAWFIX version has
    never flown - run a dry run first.

view_map:=false           default false
    Do not print the ASCII map in the terminal.

dry_run:=true             default true
    true  = does NOT arm, sends NO setpoints at all.
    false = real flight.


8. WHAT THE BANNER MUST SHOW IN A DRY RUN
------------------------------------------------------------
    Backend       : FM TensorRT (GPU) K=8
    Replan cost   : candidates 1 | budget 1.0 s | OPENBLAS_NUM_THREADS=1
                    | w_feasibility 1000
    Flying yaw    : SMOOTH follow path | tau 1.5 s | <= 30 deg/s
                    | +-60 deg of goal dir | deadband 15 deg
                    | min speed 0.05 m/s
    Battery       : min 20 %
    Guard mode    : OFF (no guards/escape)
    [BARO] baro_gain=0: NO barometric loop
    [RTH] rth_mode=replan ... rth_after_goal:=true
  and NO ASCII map block.

  If it says "HOME yaw locked", the flying_yaw_mode argument was not
  read: check the spelling and that ~/drone_ws/install/setup.bash is
  sourced.

  With keep_octomap:=true (section 9) there is also:
    Octomap       : KEPT from takeoff (keep_octomap:=true) — wiped once
                    pre-ARM only; NO wipe at HOVER->FLYING or after
                    failed replans
  Without it: "Octomap : wiped pre-ARM, at HOVER->FLYING and after
  8 failed replans (keep_octomap:=false)".


9. OCTOMAP NOT WIPED AFTER TAKEOFF (keep_octomap)        [KEEPMAP 10/02]
------------------------------------------------------------
keep_octomap:=true        default false
    Old behaviour: the octomap is WIPED up to 3 times per flight
      a. before ARM, when the height band is set    -> still wiped
      b. end of HOVER, right before FLYING           -> NO longer
      c. during FLYING / RETURN, after every 8
         consecutive failed replans ("wiping a likely
         STALE map", at most once per 20 s)          -> NO longer
    Real example, bag 9/30 17:52 (/octomap_binary): the map dropped to
    empty (48 bytes) at t=55 s (a), t=75 s (b) and t=118 s (c).

    With keep_octomap:=true only (a) remains: the map holds everything
    seen from a few seconds before takeoff, through takeoff, hover and
    flying until RETURN. (a) is kept on purpose so that data from waiting
    for GPS/EKF on the ground (people standing next to the drone, etc.)
    does not end up in the map.

    In the terminal:
      HOVER : octomap KEPT (keep_octomap:=true) — the map from
              takeoff + hover stays, no wipe
      FLYING: [MAP] 8 replans failed — stale-map wipe SKIPPED #1
              (keep_octomap:=true), map kept
      DONE  : [REAL] Octomap kept for the whole flight
              (keep_octomap:=true): N stale-map wipe(s) skipped

    CONSEQUENCE: (c) is the recovery for "ghost voxels" (false points
    stuck in the map that the camera never sees again). Without (c),
    replans can keep failing near a ghost voxel; the drone holds position
    until mission_timeout_s, then RTH / lands as usual. Avoidance of
    obstacles that ARE in the map is not reduced, but the mission can
    get stuck. For normal flights leave the default.

    dry_run:=true has no takeoff/HOVER, so there only (c) differs.

    Viewing the map (needs record_map:=true publish_3d_map:=true):
      - bag in ~/flight_maps/map_<time>/ ; the LAST /octomap_full
        message = the full map of one flight.
      - replay:  ros2 bag play ~/flight_maps/map_<time>
        RViz2: Fixed Frame = odom, Add -> octomap_rviz_plugins/
        OccupancyGrid topic /octomap_full (3D), and Map topic
        /projected_map (the 2D map the planner uses).
      - save to a file while the launch is STILL running (before Ctrl-C):
          ros2 run octomap_server octomap_saver_node --ros-args \
              -p octomap_path:=$HOME/flight_maps/map.bt
        (.ot + "-p full:=true" for the full map). Tested 10/02.
    Older bags also contain takeoff + hover, but only up to moment (b):
    play the bag and look at the messages before that moment.


10. VOXEL CONFIRMATION FILTER FOR OCTOMAP (confirm_hits)  [VOXCONF 10/06]
------------------------------------------------------------
confirm_hits:=2           default 1 (= off, old behaviour)
confirm_window_s:=2.0     default 2.0

    Problem (10/06 bags, five flights in light rain): octomap marks a
    voxel "occupied" from the FIRST hit, points beyond max_range are
    dropped before octomap (no ray clears the far side), and
    keep_octomap:=true turns off map wiping. A depth speck seen in ONE
    frame stays until landing. 61-71 % of occupied voxels in the planner
    band were hit only once, most born 3.3-4 m ahead of the nose, and
    together they blocked the way to the goal. Not only in rain: the
    9/30 dusk flight was the same.

    With confirm_hits:=2, a new depth point is passed to octomap only if
    the 15 cm voxel it falls in (odom frame, same grid as octomap) was
    hit in 2 different frames within confirm_window_s seconds. A voxel
    that passed stays accepted while it keeps being seen (60 s). ONLY the
    point cloud for octomap (/realsense/depth/points) is filtered; the
    depth image for the FM model is untouched.

    Test results (hit history of 6 recorded flights replayed through the
    same code, 2 hits / 2.0 s):
      single-hit voxels removed       96 %
      real obstacle voxels kept       99.6 %
      route to the goal open          37 of 37 moments (raw map: 29)
    DO NOT use confirm_hits:=3 : 5-15 % of real obstacle voxels are lost
    too. A 1.0 s window is also fine (98.4 % kept), same noise removal.

    In the terminal:
      voxel confirmation ON: a point reaches octomap once its 0.15 m
          voxel (odom) was hit in >= 2 frames within 2.0 s | ...
      [CONFIRM] 10.0 s: 97 frames (9.7 Hz) | N points in -> M to
          octomap, K held back (2.1 %) | accepted voxels ... |
          filter 3.1 ms/frame | TF age 20 ms | unfiltered frames:
          0 bypassed, 0 after a pause          (one line per 10 s)
    Without the option: "voxel confirmation OFF (confirm_hits < 2)
    — every point goes to octomap".

    "[CONFIRM] filter bypassed, all N points of this frame go to
    octomap: ..." = for that frame the filter did NOT run (TF odom <-
    camera missing or older than 0.5 s, an error, or almost every point
    of a large cloud rejected for 2 s) and all points were sent as in
    the old behaviour. The filter can only DROP points; it never stops
    the point cloud. Occasionally is fine; if it keeps happening, check
    MAVROS / mavros_tf_broadcaster.
    "after a pause" = the first frame after a gap > confirm_window_s
    (nothing to compare with yet) is also sent whole.

    CONSEQUENCES:
      - real obstacles enter the map slightly later: 1 frame (~0.1 s)
        when seen continuously; in the recorded data the median was
        0.3-1.1 s per voxel, and the drone was at most 0.18 m closer to
        the obstacle when its first voxel entered the map
      - things the camera catches only now and then (thin branches,
        wires, the edge of the range) do NOT enter the map until seen
        twice within 2 s
      - rays from held-back points do not mark "free" space, so there
        are more "unknown" cells. The planner is not affected
        (unknown = free), but if the guards are turned on again
        (use_lookahead_guard, blind_abort_s) test that first
      - noise that hits the same voxel twice within 2 s still passes

    With the filter on, depth_to_pointcloud also uses a fast path to fill
    the point-cloud message (7-13 ms per frame, before 30 ms for 13k
    points and 107 ms for 53k points). The message content is identical
    byte for byte.

    Recording (record_map:=true): the bag now also contains
      /realsense/depth/points_rejected   points held back by the filter
      /realsense/depth/confirm_status    filter counts, 1 Hz (JSON)
    RViz2: Add -> PointCloud2, topic /realsense/depth/points_rejected,
    Fixed Frame odom -> shows WHAT the filter dropped.
    To record the full point cloud (to try other settings offline), run
    in a second terminal while the launch is running:
      ros2 bag record -o ~/flight_maps/cloud_$(date +%H%M%S) \
          /realsense/depth/points /realsense/depth/points_rejected \
          /tf /tf_static
    (about 2 MB/s; full cloud = points + points_rejected).

    Alternative without the filter: max_range:=3.0 (every point > 3 m is
    dropped, applies to depth_to_pointcloud and octomap). In the replay
    of the same data the route to the goal also opened, but new obstacles
    are seen 1 m later. Can be combined with confirm_hits:=2.
